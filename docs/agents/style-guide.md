# Agent Style Guide

Use this guidance for agent responses, implementation notes, plans, code reviews,
code comments, and user-facing documentation.

## Precedence

Resolve conflicts in this order:

1. User requirements
2. Repository-specific instructions, terminology, and style
3. This guide
4. The linked Google developer documentation style guide

The guidance is a default, not a reason to override a clear project convention.
When a deviation is useful or necessary, state the reason and apply it
consistently.

## Accessibility

Write for readers with different abilities, backgrounds, and levels of English
fluency. Prefer clear structure, descriptive headings and links, plain language,
and text that does not depend on color, visual layout, or cultural context.

See [Google's accessibility guidance](https://developers.google.com/style/accessibility).

## Avoid Excessive Claims

Do not present uncertain conclusions as facts. Distinguish observed evidence,
inference, recommendation, and unresolved uncertainty. Avoid hype, absolutes,
and claims about correctness, safety, performance, or completeness unless the
available evidence supports them.

See [Google's guidance on excessive claims](https://developers.google.com/style/excessive-claims).

## Future Features

Do not describe planned or possible behavior as if it already exists. Use precise
language for current behavior, planned work, assumptions, and follow-up ideas.
Avoid promises about dates, availability, or outcomes that have not been
confirmed.

See [Google's guidance on future features](https://developers.google.com/style/future).

## Jargon

Use the project's established terminology. Define necessary technical terms on
first use, avoid unexplained acronyms, and prefer familiar words when they are
equally precise. Do not introduce terminology merely to make an explanation
sound more sophisticated.

See [Google's guidance on jargon](https://developers.google.com/style/jargon).

## Prescriptive Documentation

Give instructions in direct, actionable language. State prerequisites, describe
the expected result, and separate required steps from optional context. Do not
hide an instruction inside vague or promotional prose.

See [Google's guidance on prescriptive documentation](https://developers.google.com/style/prescriptive-documentation).

## Other Sources

Attribute information taken from external sources and preserve the distinction
between source material and the agent's own analysis. Follow repository policy
for citations and licenses. Do not imply that an external source validates a
conclusion it does not actually support.

See [Google's guidance on other sources](https://developers.google.com/style/other-sources).

## Timeless Documentation

Prefer durable descriptions over references to the current date, release state,
or temporary UI. When time-sensitive information is necessary, include the
relevant date, version, or condition and avoid wording that will become
misleading when the project changes.

See [Google's guidance on timeless documentation](https://developers.google.com/style/timeless-documentation).

## Voice and Tone

Be conversational, friendly, respectful, and direct without slang, hype,
figurative language, or unnecessary formality. Keep the primary purpose clear:
communicate useful information efficiently. Avoid filler, unexplained
exclamation, and phrases that minimize complexity such as "simply" or "it's
easy."

See [Google's guidance on voice and tone](https://developers.google.com/style/tone).

## Planning and Reviews

Ground plans and reviews in repository evidence. Name the files, behavior, or
observations that support a conclusion. Label assumptions and open questions,
and ask rather than inventing missing requirements. Report risks and limitations
without overstating their likelihood or impact.
