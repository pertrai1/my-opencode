# AI-Native SDLC

## Agents

### Planner

#### Overview

The SDLC kicks off the software development process, and can enter through different routes. A person has an idea, a ticket is filed, or an incident is surfaced via an alert.

When a person has an idea, they brainstorm with the LLM and produce a Markdown proto-spec.

The proto-spec generated by the LLM is human readable, version controlled, and immediately consumable by the next stage. The proto-spec is saved as an intent.md in a directory for the given spec.

Regardless of whether the intent originates from an event trigger or a person, the same steps apply: the product owner reviews and corrects the agent-written intent.md before it is committed.

#### How to Execute

1. The originator describes the problem to the `planner` agent in their own words. The originator may describe what they cannot do today, who is affected by the idea, what better looks like, or what is out of scope. No formal language is required.
2. Brainstorm until the idea is concrete. The `planner` agent asks the questions an analyst would ask: scope, users, constraints, and what success looks like.
3. Ask the `planner` agent to write the result as intent.md using the @planner.md template. This can cover the problem, proposed outcome, affected users and systems, constraints, and open questions.
4. The originator corrects anything the `planner` agent misunderstood.
5. Commit intent.md to version control. Author and timestamp join the record, and the `design` agent picks the idea up from there.

### Designer

#### Overview

Once the product owner approves the intent.md, Claude takes it and produces a requirements and design spec. This is guided by the organization's skills for brand, security, compliance, and UX.

The product owner reviews that spec, but doesn't write it. The goal of this process is to create a spec the engineering team can plan against, with flagged areas of concern.

#### Overview

Once the user approves the intent.md, handoff goes to the `designer` agent that takes intent.md and produces a requirements and design spec. This is guided by brand, security, compliance, and UX.

The user reviews that spec, but doesn't write it. The goal of this process is to create a spec the engineering team can plan against, with flagged areas of concern.

#### Prompt

Read the attached intent.md and produce a requirements and design spec for integrating it into our existing codebase. Apply the skills available to you so the plan conforms to our brand guidelines, security policies and UX standards. Document the spec fully as spec.md, ready to hand to the engineering team. Describe clearly any areas of concern, especially where you cannot satisfy contradicting policies.

### Architect

#### Overview

User starts `architect` agent, gives the approved spec.md, and let it interview them, iterating on the plan until they are happy with it.

Design review happens before any code is generated, when changing course is still a matter of editing a document. Plan mode enforces this itself, since `architect` agent cannot edit files until the engineer accepts the plan. The plan and its revisions are logged along with who accepted it. Routine changes are approved by the engineer, and anything the organization classes as higher risk goes to a tech lead or architect.

#### How to Execute

1. The engineer starts the session in plan mode.
2. The engineer gives `architect` agent the intent.md and the spec.md and asks for an implementation plan that names the files that change, the order of the work, and the tests that prove it.
3. Interrogate the plan by asking what the change could break, which step is most risky, and what other options `architect` agent chose not to do.
4. Iterate until an engineer who has never seen the conversation could implement the change from the plan alone.
5. Commit the approved plan as plan.md.
6. Accept the plan and let `builder` agent implement. With a solid plan, the implementation is often a single pass.
7. When `builder` agent departs from the plan, update plan.md in the same commit. Consider using a hook to enforce synchronization between the two.
